## 1. AI能力边界

### 1.1 AI可独立完成的任务

以下任务AI可在明确需求后直接执行，无需逐行确认：

- **功能实现：** 根据明确需求实现功能模块
- **测试编写：** 编写单元测试和集成测试
- **代码重构：** 提取函数、重命名、消除重复、优化结构
- **技术方案设计：** 输出技术方案文档（须用户确认后方可实施）
- **Bug修复：** 问题描述清楚时的修复
- **技术文档：** API文档、部署文档、使用说明
- **样式调整：** 颜色、间距、字体大小、布局微调
- **配置优化：** 工具链配置、环境变量、CI脚本

### 1.2 AI不可独立完成的任务（必须用户介入）

以下任务AI不得独立完成，必须经用户确认或亲自执行：

- **需求理解和确认：** 需求模糊时必须暂停并讨论
- **架构方向性决策：** 技术栈替换、架构模式变更
- **生产环境部署：** 任何涉及生产环境的操作
- **安全认证核心逻辑审查：** JWT密钥、密码策略、权限模型
- **凭证管理：** 数据库密码、API密钥的生成和管理
- **数据安全策略变更：** 数据分级调整、脱敏规则变更
- **破坏性变更：** 删除已有功能、废弃公共接口

## 2. 决策边界矩阵

### 2.1 决策权限分级

| 决策类型 | 示例 | 决策主体 | 说明 |
|----------|------|----------|------|
| **AI自主** | 变量命名、函数拆分 | AI | 执行后立即汇报 |
| **AI自主** | 提取公共函数、消除重复 | AI | 执行后立即汇报 |
| **AI自主** | 颜色、间距、字体大小 | AI | 执行后立即汇报 |
| **AI自主** | 正常/边界/异常测试用例 | AI | 随代码一起提交 |
| **AI自主** | 问题明确的Bug修复 | AI | 修复后说明根因 |
| **用户确认** | 新增表、字段变更 | 用户 | 须先讨论再执行 |
| **用户确认** | URL、请求/响应字段变更 | 用户 | 须先讨论再执行 |
| **用户确认** | 新增第三方库、版本升级 | 用户 | 须评估影响 |
| **用户确认** | 分层变更、技术栈替换 | 用户 | 须出ADR |
| **用户确认** | 角色定义、权限范围 | 用户 | 须评估安全影响 |
| **用户确认** | 废弃接口、删除模块 | 用户 | 须评估兼容性 |
| **用户确认** | 认证方式、加密算法 | 用户 | 须评估安全影响 |

### 2.2 决策流程图

```
收到任务
  │
  ├─→ 判断：是否属于AI自主范围？
  │       │
  │       ├─→ 是 → AI直接执行 → 完成后汇报变更清单
  │       │
  │       └─→ 否 → 判断：是否有明确方案？
  │               │
  │               ├─→ 是 → 输出方案 → 用户确认 → 执行
  │               │
  │               └─→ 否 → 暂停讨论 → 明确需求 → 重新评估
```

## 3. 人机协作节奏

### 3.1 标准协作流程

```
迭代开始
  │
  ├─→ 用户：确认需求范围和验收标准（约15分钟）
  │       产出：验收标准清单（可验证的通过条件）
  │
  ├─→ AI：设计技术方案，输出ADR草案
  │       产出：ADR文档 + 技术方案说明
  │
  ├─→ 用户：确认方案
  │       ├─→ 有异议：讨论后AI修改，循环直至确认
  │       └─→ 无异议：继续
  │
  ├─→ AI：实现代码 + 测试（并行进行）
  │       产出：源代码 + 测试代码
  │
  ├─→ AI：执行自检（类型检查 + 测试 + 安全扫描）
  │       产出：自检报告（通过/失败项清单）
  │
  ├─→ AI：输出变更清单（Markdown格式）
  │       产出：变更摘要文档
  │
  ├─→ 用户：Review代码（关注业务逻辑和安全）
  │       ├─→ 有修改意见：AI修复，循环直至满意
  │       └─→ 满意：继续
  │
  └─→ 用户：验收通过，合并到main分支
```

### 3.2 沟通节奏

| 场景 | 沟通方式 | 响应要求 |
|------|----------|----------|
| 正常进度 | AI完成后统一汇报 | 无需实时响应 |
| 遇到技术难点 | 立即暂停，提出方案选项 | 用户确认后继续 |
| 需求不明确 | 立即暂停，列出待确认问题 | 用户澄清后继续 |
| 发现潜在风险 | 立即提醒，说明影响 | 用户决策 |
| 自检失败 | 说明失败项，提出修复方案 | 用户确认后修复 |

### 3.3 迭代节奏建议

**每个迭代周期：** 建议1-3个功能点，不宜过多。

**单次交付粒度：**
- 一个功能模块（如"登录功能"）
- 或一个API接口（如"用户列表查询"）
- 或一个页面（如"知识库管理页"）

**交付频率：** 每个功能点完成后立即交付Review，不积累多个功能一起交付。

## 4. 代码溯源标记

### 4.1 标记目的

- 区分AI生成代码和人类代码
- 追溯代码的生成背景和验证状态
- 便于后续维护和审计

### 4.2 标记方式

**方式一：文件头部注释（适用于全新文件）**

```python
"""
智能问答平台 - 用户认证服务

生成信息:
- AI辅助生成: 是
- 生成日期: 2026-07-30
- 功能描述: 支持本地/LDAP/SSO三种认证模式
- 验证状态: pytest tests/unit/test_auth.py 全部通过
- 版本: V1.0

修订记录:
- 2026-07-30 V1.0 初始版本（AI生成）
- 2026-08-01 V1.1 修复Token刷新问题（人工修改）
"""
```

**方式二：Git提交标记（适用于增量修改）**

```bash
git commit -m "feat(auth): 实现LDAP统一认证

- 支持Active Directory和OpenLDAP
- 自动同步用户部门和职位信息
- 登录失败5次自动锁定账号

Co-authored-by: Claude <ai-assistant>
AI-Generated: true
Reviewed-by: [用户姓名]"
```

**方式三：行内注释（适用于关键逻辑）**

```python
# AI-GENERATED: 2026-07-30
# 说明: 以下逻辑处理LDAP用户自动同步
# 验证: test_ldap_sync.py 通过
async def sync_ldap_user(ldap_user: dict) -> User:
    ...
# END AI-GENERATED
```

### 4.3 标记规则

- 全新文件：使用方式一（文件头部注释）
- 增量修改：使用方式二（Git提交标记）
- 复杂逻辑块：使用方式三（行内注释）
- 简单修改（单行、重命名）：方式二即可

## 6. AI自检清单

### 6.1 自检目的

AI在提交代码前必须完成自检，确保代码质量达到可Review的标准。

### 6.2 自检清单

**功能性：**
- [ ] 完整实现了需求描述的全部功能点
- [ ] 边界情况已处理（空值、越界、超时）
- [ ] 错误处理覆盖所有可能的异常路径
- [ ] 无TODO/FIXME遗留（如有，已在变更清单中说明）

**安全性：**
- [ ] 所有用户输入已校验（类型、长度、格式）
- [ ] 权限检查已添加（如涉及管理员/敏感操作）
- [ ] 无硬编码敏感信息（密码、密钥、Token）
- [ ] 无`print`调试语句（使用日志框架）
- [ ] 无`eval`/`exec`/`pickle`使用
- [ ] 数据库操作使用ORM/参数化查询

**可测试性：**
- [ ] 新增代码有对应的单元测试
- [ ] 测试通过（pytest / vitest）
- [ ] 测试覆盖率不低于基线（后端80%，前端70%）
- [ ] Mock使用恰当（只Mock外部依赖）

**质量：**
- [ ] 代码通过类型检查（mypy --strict / vue-tsc --noEmit）
- [ ] 代码通过格式检查（black / prettier）
- [ ] 代码通过风格检查（ruff / eslint）
- [ ] 无未使用的导入或变量
- [ ] 函数长度合理（不超过50行，超过则拆分）
- [ ] 嵌套层级合理（不超过4层）

**兼容性：**
- [ ] 接口变更不影响现有调用方（或已同步更新）
- [ ] 数据库变更有迁移脚本（向后兼容）
- [ ] 配置文件变更有默认值（不影响已有部署）
- [ ] 文档已同步更新

### 6.3 自检失败处理

| 失败项 | 处理方式 |
|--------|----------|
| 类型检查失败 | 修复类型错误，或添加合理的`# type: ignore`注释 |
| 测试失败 | 修复代码或更新测试，不跳过失败测试 |
| 覆盖率不足 | 补充测试用例，或申请豁免（须说明理由） |
| 安全扫描告警 | 必须修复，除非确认为误报（须说明理由） |

## 7. 代码审查规范

### 7.1 审查者（用户）关注点

**必须审查：**
- [ ] 业务逻辑是否正确实现了需求
- [ ] 安全边界是否完整（输入校验、权限检查、数据脱敏）
- [ ] 性能是否合理（N+1查询、大结果集、内存泄漏风险）
- [ ] 错误处理是否覆盖边界情况
- [ ] 数据库变更是否向后兼容

**建议审查：**
- [ ] API设计是否RESTful、是否向前兼容
- [ ] 日志是否恰当（无敏感信息、关键节点有记录）
- [ ] 代码可读性（命名是否清晰、注释是否必要）

**可快速浏览：**
- [ ] 单元测试（检查覆盖率即可，不逐行审查）
- [ ] 样式调整（运行效果验证即可）
- [ ] 配置文件（检查变更范围即可）

### 7.2 被审查代码应具备

- [ ] 清晰的变更范围说明（变更清单）
- [ ] 通过全部自动化检查（CI绿色）
- [ ] 测试用例覆盖新增逻辑
- [ ] 文档同步更新
- [ ] 无硬编码敏感信息

### 7.3 审查意见格式

```markdown
## Review意见

### 必须修复（阻塞合并）
- [ ] 问题1：...（原因 + 建议修改方式）
- [ ] 问题2：...

### 建议优化（非阻塞，可后续迭代）
- [ ] 建议1：...（原因 + 可选方案）
- [ ] 建议2：...

### 疑问
- [ ] 问题1：...（需要AI澄清）

### 赞赏
- [ ] 某处实现很优雅
```

## 8. 故障处理

### 8.1 故障分类与处理

| 场景 | 处理流程 | 责任主体 | 时间要求 |
|------|----------|----------|----------|
| Bug修复后复发 | AI分析根因 → 补充回归测试 → 更新测试策略 | AI | 当前迭代 |
| 性能问题 | AI提供优化方案 → 用户确认 → 实施 → 补充性能测试 | AI + 用户 | 当前迭代 |
| 安全漏洞 | 立即修复 → AI编写事后分析 → 更新安全检查清单 | AI + 用户 | 24小时内 |
| 需求理解偏差 | 用户澄清需求 → AI重新实现 → 用户加强验收 | 用户 + AI | 当前迭代 |
| 技术方案缺陷 | 重新评估ADR → 必要时废弃重写 | 用户 + AI | 视影响范围 |
| 规范违反 | 修复代码 → 分析规范合理性 → 必要时修订规范 | AI + 用户 | 当前迭代 |

### 8.2 事后分析模板

```markdown
# 事后分析：[问题简述]

## 发生时间

## 问题描述

3. 系统性原因：...

## 影响范围
- 影响模块：...
- 影响用户：...
- 数据影响：...

## 修复措施
1. ...
2. ...

## 预防措施
1. ...
2. ...

## 经验教训
...

## 相关改进
- [ ] 更新规范
- [ ] 补充测试
- [ ] 更新检查清单
```
